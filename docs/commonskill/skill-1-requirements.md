# Skill-1: 需求结构化拆解

## 触发时机

- 全新项目启动，完成 skill-0 冷启动握手之后
- 新增功能模块，需要在开发前明确边界

---

## 执行步骤

### 第一步：主动追问，消除模糊

对用户提供的需求描述，逐项确认以下维度。如果用户未提及，必须追问：

**功能边界**
- 这个功能的输入是什么？输出是什么？
- 有哪些情况不在本次开发范围内？

**实时性要求**
- 响应时间要求是多少？（ms 级？us 级？）
- 有没有硬实时截止时间？
- 涉及中断吗？中断优先级是什么？

**资源约束**
- Flash / RAM 的上限预留是多少？
- 有没有栈深度限制？

**通信协议**
- 使用什么外设和协议？（UART / I2C / SPI / CAN …）
- 帧格式是什么？有没有现成协议文档？

**功耗 / 安全**
- 有没有低功耗要求？（睡眠模式？唤醒源？）
- 有没有看门狗、异常复位要求？
- 量产场景有没有特殊约束？

### 第二步：输出开发规格文档

追问完成后，生成以下格式的文档，保存到 `.context/project.context.md` 的顶部：

```markdown
## 开发规格：[功能名称]

### 功能定义
- 输入：
- 输出：
- 不包含：

### 性能约束
- 响应时间：
- 中断优先级：
- Flash 预算：  / RAM 预算：
- 栈深度上限：

### 通信协议
- 外设：
- 帧格式：（附协议文档路径或摘要）

### 异常处理要求
- 超时行为：
- 错误重试次数：
- 失败后的恢复机制：

### 验收标准

#### 功能验收
- [ ] [具体可测试的行为，例如：BME280 温度读数误差 < 0.5℃]
- [ ]

#### 可靠性验收（嵌入式必须项）
- [ ] 中断安全：[具体说明涉及的 ISR 和共享资源]
- [ ] 并发安全：[是否有多任务访问同一资源，保护机制是什么]
- [ ] 长时间稳定：[连续运行 X 小时无异常复位]
- [ ] 异常恢复：[断电重启后能否正常恢复工作状态]
- [ ] 边界测试：[极限输入、最大负载、最低电压下的行为]

### 不可接受的情况
- [明确列出：什么情况下算失败，例如：任何情况下不得出现 HardFault]
```

### 第三步：让用户确认规格文档

输出规格文档后，等待用户确认或修改。未经用户确认不得进入开发阶段。

---

## 执行规则

- 宁可多追问一次，不要带着模糊假设进入开发
- 验收标准必须是可测试的具体描述，禁止写"功能正常"这类不可测量的表述
- 可靠性验收条目不可省略，这是嵌入式与普通软件开发的核心差异
- 如果用户说"先开发再说"，记录到 decisions.log.md，并在 todo 中标注"验收标准待补充"
