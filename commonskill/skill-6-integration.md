# Skill-6: 集成验收 + 知识沉淀

## 触发时机

- 所有模块在 skill-5 中完成单独验证
- `project.context.md` 中无 🚧 状态的模块
- 准备交付或归档项目

---

## 执行步骤

### 第一步：集成冒烟测试

将所有模块合并，执行最基础的端到端验证：

- 完整功能链路跑通一次（正常路径）
- 确认模块间接口无冲突（对照 skill-4 中定义的接口契约）
- 串口输出所有模块的启动状态

发现集成问题：回到 skill-5 处理，不在本 skill 内迭代。

### 第二步：可靠性验收

对照 skill-1 中定义的可靠性验收标准，逐项测试：

**中断安全检查**

对照 skill-4 的实时性声明表，逐条验证：

```
对每个"在中断中运行"的模块：
1. 确认共享资源有保护机制（volatile / 原子操作 / 临界区）
2. 在中断中没有调用阻塞函数（HAL_Delay / printf / malloc）
3. ISR 执行时间在截止时间内（通过 GPIO 翻转 + 示波器估算）
```

**竞态检查**

```
对每个多任务共享的资源：
1. 是否有互斥保护？
2. 是否存在读-改-写的非原子操作？
3. 关中断保护的临界区是否尽可能短？
```

**栈深度检查**

解析 MAP 文件中的栈使用情况：
- 各任务栈是否在分配范围内
- 主栈 + 中断嵌套深度是否超限
- 如有 FreeRTOS：检查 `uxTaskGetStackHighWaterMark` 结果

**长时间稳定测试**

按 skill-1 规格中约定的时长运行（最少 30 分钟，建议 2 小时）：

- 监控串口日志是否有异常复位、HardFault、看门狗触发
- 检查内存：关键变量是否漂移，堆/栈是否持续增长
- 检查外设：I2C/SPI 是否出现偶发错误恢复

**边界测试**

- 最大负载：同时触发所有外设和任务
- 极限输入：传感器返回最大/最小/无效值时的行为
- 断电重启：掉电重启后状态是否正确恢复

### 第三步：最终资源确认

读取最终 MAP 文件，记录交付时的资源用量：

```markdown
## 最终资源用量
- Flash：X KB / Z KB（占比 X%）
- RAM：X KB / Z KB（占比 X%）
- 最大栈深度：X KB（来自 [模块名]）
- 对比基线：Flash +X KB，RAM +X KB
```

### 第四步：生成交付文档

输出以下文档，保存到 `docs/` 目录：

**`docs/README.md`** — 项目概述

```markdown
# [项目名] 固件说明

## 功能概述
## 硬件要求
## 编译和烧录方法
## 串口输出说明
## 已知限制
```

**`docs/module-interface.md`** — 模块接口文档

列出所有对外接口，包含函数签名、参数说明、返回值、调用约束（是否可在中断中调用）。

**`docs/resource-report.md`** — 资源报告

Flash/RAM 用量、各模块占用分析、栈深度分析。

### 第五步：知识沉淀 — 写回 knowledge-base

这是让系统越用越强的关键步骤。对本项目的经验按类型分类：

**写入 `known-bugs.md`**

格式：
```markdown
## [芯片型号] [外设] [问题描述]

- **症状**：
- **根因**：
- **解决方案**：
- **参考**：[数据手册章节 / Errata 编号]
- **来源项目**：[项目名] [日期]
```

**写入 `hal-patterns.md`**

格式：
```markdown
## [外设类型] [使用模式名称]

**适用场景**：
**关键代码**：
**注意事项**：
**来源项目**：[项目名] [日期]
```

**写入 `debug-recipes.md`**

格式：
```markdown
## [问题类型] [症状描述]

**排查路径**：
1. 先检查 ...
2. 如果 ... 则 ...
3. 最终通过 ... 确认

**结论**：
**来源项目**：[项目名] [日期]
```

**写入 `rtos-patterns.md`**（如项目使用 RTOS）

---

### 第六步：归档项目上下文

将 `.context/` 目录的三个文件标记为归档状态：

在 `project.context.md` 顶部追加：

```markdown
> **状态：已归档** — 归档日期：[日期] · 交付版本：[git tag 或版本号]
```

---

## 执行规则

- 可靠性验收条目不得省略，这是嵌入式与普通软件交付的核心差异
- 长时间稳定测试不得缩短，最少 30 分钟
- 知识沉淀不是可选步骤，每个项目都应至少贡献一条经验到 knowledge-base
- 发现集成问题不在本 skill 内处理，返回 skill-5
